# PropSnap

Chrome extension (Manifest V3, WXT framework) that captures property listing data from UK property websites and enriches it with full street addresses via the EPC Register API.

## What it does

Users browse Rightmove, Zoopla, or OpenRent listings. They click "Capture" in the popup. The extension extracts listing data from the page, calls the EPC API to get the full street address (which listing sites hide), and saves everything locally with CSV export.

## Architecture

- **Content scripts** (`entrypoints/content/`) — inject into listing pages, extract data using site-specific adapters
- **Background service worker** (`entrypoints/background.ts`) — handles EPC API calls (cross-origin), storage, CSV export
- **Popup** (`entrypoints/popup/`) — UI for capture button, result display, settings, export
- **Listing page** (`entrypoints/listing/`, built as `listing.html?key=source:listingId`) — one saved listing with the deal calculators, opened from the dashboard's Details button. Calculator maths is pure in `src/services/calculators.ts` (tested): purchase tax (England SDLT with first-time buyer relief and the 5% additional-property surcharge; Wales LTT main and higher rates; tables for 2026/27, check each April), monthly mortgage (interest only or repayment; an empty term counts as `DEFAULT_TERM_YEARS`, 25), buy-to-let (yields, cashflow, return on cash), BRR (money left in after the refinance), flip (`flip`: sells at the value after the works; optional bridging loan with interest rolled up and paid from the sale, lender's fees paid up front; holding and selling costs; profit before tax, profit on cost, cash needed, return on cash) and HMO (`hmo`: rooms × rent per room, bills, HMO management %, the licence fee spread over the years it lasts; uses the purchase, mortgage, works as the conversion cost and the repairs %). A sourcing fee (`sourcingFee`, £ or % of the price) and the user's own costs (`customCosts`, max 10, one-off or monthly, checked by `cleanCustomCosts`) go into every strategy: one-off with the purchase, monthly with the running costs. This is the only list of extra costs: the old single "Other costs (£ a month)" field (`otherMonthly`, before 0.4.1) is gone, and `dealInputsFor` turns a saved figure into a monthly cost named "Other costs", so the numbers stay the same. `taxRegionFromPostcode` picks England or Wales and is not sure on border districts (`BORDER_DISTRICTS`, the districts with homes in both countries from the ONS postcode directory, and all of HR), where the page asks the user to check. `dealInputsFor` prefills the price (or the rent on a rent listing) and region from the listing
- **Sold prices** (on the listing page) — HM Land Registry Price Paid Data via the public SPARQL endpoint `https://landregistry.data.gov.uk/landregistry/query` (POST `query=`, `Accept: application/sparql-results+json`, no key; host permission in `wxt.config.ts`). `src/services/land-registry.ts` builds two queries: every sale in the full postcode, and every sale on the same street within the postcode district (`STRSTARTS(?postcode, "CF24 ")`); postcode, outcode and street are checked against strict patterns before they go into a query. It parses the W3C SPARQL JSON answer into `SoldPrice` (price, date, saon/paon/street/town/postcode, type, tenure, new build, `standard` = false for category B sales such as repossessions) and merges both answers by transaction URI. When one search fails, `fetchSoldPrices` returns the other's sales with that search in `failed`, and the page (and report) says the sales are only part of the picture. `fetchSoldPricesCached` keeps each area's whole answer (never a half one) for a day in the session cache; the page says how old a kept answer is, and Refresh asks again. `src/services/sold-prices.ts` (pure, tested) finds the street (`soldPriceArea`: from the full address, else the display address; skips building names; knows Welsh "Heol …" names; spells out St/Rd/Ave), maps the listing type (`lrTypeFor`), picks out this home's own past sales (`isSameHome`: same number, street and flat number) and works out median, range and asking price against the median from standard sales only. `findFlips` finds homes resold within `FLIP_MONTHS` (24) for at least `FLIP_MIN_RISE_PCT` (10%) more (same saon/paon/street/postcode; a new build's first sale is not counted), shown as Flipped nearby under the sold table and in the report, with the same type and years filters applied to the resale. The page filters by type (`typeChoices`: e.g. "Terraced only" / "All houses" / "All types"; a flat gets "Flats only" / "All types") and years, warns when fewer than `FEW_SALES` (5) standard sales make the figures, can copy the median into the BRR "Value after the works", and shows the Open Government Licence attribution, which the licence requires
- **Area checks** (listing page, after the EPC) — `src/services/area-checks.ts` (parsing pure, tested on trimmed real answers in `tests/fixtures/area/`). Position: the listing's map position (`pointFromListing`, Great Britain only), else the full postcode's centre from postcodes.io. Each country's maps cover only that country, so `areaCountries` picks the home's country from the postcode (both on a border postcode or with none) and only those services are asked. Flood: Environment Agency Flood Map for Planning for England (OGC API `geoservices/datasets/04532375-…/collections/Flood_Zones_2_3_Rivers_and_Sea/items?bbox=`; the service matches by bounding box, so `eaFloodZoneAt` checks the point against each shape with `pointInGeometry`, holes taken out, and keeps the highest zone) and Natural Resources Wales for Wales (DataMapWales WFS `inspire-nrw:NRW_FLOODZONE_RIVERS_SEAS_MERGED`, `cql_filter=INTERSECTS`, the server checks the point); `combineFlood` takes the highest, and `combineFlood` / `combineConservation` give null (could not check), never "none", when one source failed and the rest found nothing. Conservation areas: planning.data.gov.uk `entity.json?dataset=conservation-area&latitude=&longitude=` (England) and DataMapWales `geonode:conservation_areas_wales`. Article 4: planning.data.gov.uk `article-4-direction-area`; `permitted-development-rights` is `;`-separated codes, names from the `permitted-development-right` dataset (`rightsNames`, kept 30 days); `hmo` when it removes 3L ("Small HMOs to dwellinghouses and vice versa") or names HMOs. Wales has no Article 4 map (not asked there; `article4` is `[]`): none found there is unknown, not clear (`summariseArea(…, { wales })` keeps `hmoArticle4` null). National planning data does not yet hold every council's areas, so the page says "none found", never "none". Crime: data.police.uk `crimes-street/all-crime` at the latest month (`crime-last-updated`), about a mile around, counted by category (`summariseCrimes`). Every source runs on its own (`failed` lists the ones that did not answer); answers are kept a week in the session cache, but not when a check failed. The short `AreaSummary` (flood zone, conservation names, Article 4 count, HMO Article 4, crimes) is saved on the listing (`setAreaSummary`, under the lock, and only while the saved listing is in the same place (`samePlace`) as the page that checked it; a check that failed keeps its last result through `summariseArea(…, { previous })`, and the summary then keeps the earlier date; kept on a new capture in the same place) for the dashboard (warning chips and an area filter: no HMO Article 4, not in a flood zone, not in a conservation area, has a warning; homes never checked never match), the report (Area checks section) and CSV (Flood Zone, Conservation Area, Article 4 Directions, HMO Article 4, Street Crimes, Area Checked). Host permissions for all five services are in `wxt.config.ts`. A guide only, with the Open Government Licence line
- **Deal pipeline** — per listing: stage (New, Researching, Viewing booked, Offer made, Offer accepted, Bought, Offer rejected, Not interested), a summary (shown as "Summary", saved as `notes`, max 5,000 characters: the main points kept up to date; dated notes and calls go in the timeline) and a follow-up date (YYYY-MM-DD, compared with the user's local date). `src/services/pipeline.ts` (pure, tested): `STATUSES`, `cleanPipeline` (storage values checked; "New" with nothing else is no data), `followUpState` (overdue / today / soon = within 7 days / later; none on a closed deal), `isDue`. Edited on the listing page (saved as the user types) and as a stage drop-down on the dashboard, which also has a stage filter (all, active deals, follow-ups due, one stage), Stage sort, the summary and every timeline note and call in search, and Active deals / Follow-ups due counts. CSV gets Stage, Follow Up and Summary columns
- **Labels, hiding, timeline and agents** — `src/services/crm.ts` (pure, tested). Labels: `BUILT_IN_LABELS` (Potential flip, BRR, Buy-to-let, HMO, Needs work, Motivated seller, Do not contact) plus the user's own (max 30 characters, 20 per listing, case ignored, `allLabels` offers every label used). A listing can be hidden; the dashboard leaves hidden homes out by default (`hidden` filter: hide / show / only, with a count). Activity timeline (`activity` in user data, oldest first, max 300, text max 2,000): notes, calls with an outcome (`CALL_OUTCOMES`), letters sent and stage changes, which `updatePipeline` adds itself (a change back to the previous stage within `UNDO_STAGE_MS`, 10 minutes, removes the stage entry instead: an undone mis-click; a call is never removed). `logCall` saves a call; an outcome that is a stage (`stageForOutcome`: viewing booked, offer made, accepted, rejected) also moves the deal to that stage, as one entry (the call with `stage` set, shown as "stage moved to …"), so calls and stages never disagree. `timeline` adds the first capture and each price change, newest first; the user can delete their own entries. Agents: `agentKey` (agent name and branch, normalised), `groupByAgent` for the dashboard's "Group by agent" view (phone, homes, last call, note), and one note per agent in `propsnap_agents` (`saveAgentNote`), shared by every listing from that agent and shown on the listing page with the agent's other saved homes. The dashboard has a label filter, labels in search, label chips and "Called N days ago" under the stage, and Hide/Unhide. CSV gets Labels, Hidden and Last Call columns; the report shows labels and the newest 15 timeline entries only when the notes box is ticked
- **Property report** (listing page, "Save report as PDF") — `src/services/report.ts` `buildReport` (pure, tested) turns what the page shows now (listing, price history, sold prices with the filters picked, calculator numbers for the strategies ticked under Report options, and the stage and notes only when that box is ticked) into sections; a strategy box the user has not touched follows `defaultStrategies` (buy-to-let always, BRR and flip once works or a new value are typed, HMO once rooms and a room rent are). Branding (`src/services/branding.ts`, key `propsnap_branding`, one for every report): company name, contact lines, colour and a PNG/JPEG/WebP/GIF logo as a data URL (no SVG, max `LOGO_MAX_CHARS`), checked by `cleanBranding`; the report puts them in a header, uses the colour for the bar and headings (`headingColour` falls back to dark grey when the colour is too light to read) and the footer says "Prepared by …"; the page renders them into `#report`, sets the document title (the PDF file name) and calls `window.print()`. `#report` is hidden on screen, and an `@media print` stylesheet hides everything else. Deal figures are left out without a price, BRR unless works or a new value are entered. It carries the Land Registry licence line and a not-advice footer. Nothing leaves the computer
- **Viewing planner** (`entrypoints/planner/`, built as `planner.html`) — the dashboard's tick boxes plus "Plan viewings (n)" open `planner.html?keys=a,b` (ticked homes replace the plan's homes; times kept); with nothing ticked the button opens the saved plan. The plan (`propsnap_plan`: keys in order, HH:MM per key, date, start text, minutes per viewing) is checked by `cleanPlan` and saved on every change. `src/services/viewing-plan.ts` (pure, tested): `bestOrder` (nearest neighbour from every start, shortest path kept, by straight-line distance; homes with no map position last), `routeKm`, `mapsPlace` (full address, else lat,lng, else listing address), `routeLinks` (Google Maps `dir/?api=1` links, no origin = user's location, split every 10 stops), `timeClashes`, `calendarFile` (.ics, one event per timed viewing, `TZID=Europe/London` with a VTIMEZONE, RFC 5545 escaping and 75-byte folding). No new permissions
- **Letters to owners** (`entrypoints/letters/`, built as `letters.html?keys=a,b`) — opened from the dashboard's "Letters (n)" button (the same tick boxes as the planner) or a listing's "Write a letter". `src/services/letters.ts` (pure, tested): three starting letters (`DEFAULT_TEMPLATES`, each ending with how to ask for no more letters), editable and kept in `propsnap_letters` with the sender's name and sign-off (`cleanLetterSettings` brings back a missing built-in; "Back to the original wording" resets one), `fillTemplate` ({street}, {address}, {date}, {your name}, {company}, {contact}; case ignored, unknown ones left), `recipientLines` ("The Owner", title-cased address lines, postcode last), `streetOf`, and `letterFor`, which writes only to an `exact` or `user_choice` full address and never to a best guess, a home with no full address, or one with the built-in "Do not contact" label (`DO_NOT_CONTACT_LABEL` in `crm.ts`), giving the reason instead. The letterhead (company, contact, colour, logo) is the report branding, not a second copy. One letter per printed page (`@media print`). "Mark as sent" logs a `letter` activity on each home under one lock (`logLetters`), shown as "Letter sent" in the timeline and as "last letter" on the page. The page carries a short UK note (not legal advice): no named people, say who you are, stop when asked, be honest, the agent's contract may still apply, ICO guidance
- **User data** (`src/services/user-data.ts`, key `propsnap_user_data`, map of `source:listingId`, holding `deal`, `pipeline`, `labels`, `hidden` and `activity`; changes go through `updateEntry` under the lock) — what the user types for a listing, kept apart from the captured listing so a new capture never overwrites it. The calculator saves only the numbers that differ from the listing's figures, so a new price still flows in. Deleting a listing or clearing all removes it too (clearing all also removes the agent notes)
- **Dashboard** (`entrypoints/dashboard/`, built as `dashboard.html`) — full-page table of saved listings, opened from the popup's Dashboard button: search, site/match/price-change/stage filters, sorting, tick boxes for the viewing planner, details, open, delete, clear all, CSV export. Reads `chrome.storage.local` directly and redraws on `storage.onChanged`. Filter/sort logic is pure in `src/services/dashboard-view.ts` (tested)

## Site adapters (`src/adapters/`)

Each site exposes data differently. `tests/adapters.test.ts` runs each adapter's `extract()` on a small page built the way that site builds its listing pages (DOM from `linkedom`); when a site changes its page, put a saved copy of the real page in there. Each site's listing URL patterns live in `src/adapters/listing-urls.ts`, with `checkedListingId`: the listing number comes from the web address, and a page whose data names another listing (left over after the site changed listing without a full load) is refused with "Reload the page"; the popup decides "is this a listing page" with `listingSiteForUrl` (the same patterns the content script uses), so it never loads the extraction code.

### Rightmove (`rightmove.ts`)
- Data source: `window.__PAGE_MODEL` — packed JSON format (schema map at index 0, values by index). Read from the inline script first; when that copy names another listing (the site moved on without a full load), the live page model is read instead
- Content scripts can't access page JS vars, so we inject a `<script>` element and pass data back via CustomEvent (`__PROPSNAP_DATA__`)
- Only gives partial postcode from address string — needs EPC for full postcode

### Zoopla (`zoopla.ts`)
- Data source: JSON-LD (`<script type="application/ld+json">`) with `@type: "RealEstateListing"`
- Also regex-parses analytics tracking data from script tags for `branch_name`, `listing_id`, `outcode`, `incode`; the scripts that name the listing number from the web address are read first, as the page can hold other homes' data too
- Gets full postcode by combining outcode + incode
- Page data uses codes (`offers_over`, `share_of_freehold`, `semi_detached_house`, `flat`); `zooplaLabel` turns the price wording, type, tenure and furnishing into words ("Offers over", "Semi-detached house"). `withPriceHistory` compares the price wording ignoring case and underscores, so a listing saved with the code gets no extra history point when it is captured again

### OpenRent (`openrent.ts`)
- Data source: Server-rendered HTML, DOM scraping via `querySelector`
- Parses page title for bedrooms/type/address
- Extracts full postcode from broadband comparison link (`/comparebroadband?postCode=SW1P%201LQ`)
- Reads HTML table rows for rent/deposit/furnished/EPC (the band only, or "Exempt" / "Not required")

## EPC API (`src/services/epc-api.ts`)

- Endpoint: `https://api.get-energy-performance-data.communities.gov.uk/api/domestic/search?postcode=...`
  (the old `epc.opendatacommunities.org` API was retired on 30 May 2026)
- Docs: https://get-energy-performance-data.communities.gov.uk/api-technical-documentation
- Auth: Bearer token (user enters in settings)
- Response: `{ data: [ { addressLine1-4, postTown, postcode, currentEnergyEfficiencyBand, registrationDate, uprn, certificateNumber } ] }`; 404 means no certificates
- Only searches with a **full** postcode; a half postcode (e.g. `CF14`) returns `no_postcode` instead of guessing
- Keeps the newest certificate per home, then ranks candidates in `src/services/epc-match.ts` (pure, unit tested in `tests/`):
  house/flat number (a clash rules a home out), floor area, flat vs house (a clash rules a home out), built form, bungalow on both sides (+1, never a clash), habitable rooms vs bedrooms, address words, postcode
- Search results have no bedrooms/property type, so for the homes still close after the first pass (max 10) we fetch the full certificate (`GET /api/certificate?certificate_number=...`: `dwelling_type`, `habitable_room_count`, `total_floor_area`) and rank again. Newer (RdSAP 2026) certificates wrap values (`dwelling_type: { value: "Detached house" }`), give `property_type`/`built_form` as codes (0 House, 1 Bungalow, 2 Flat, 3 Maisonette / 1 Detached, 2 Semi-Detached, 3 End-Terrace, 4 Mid-Terrace) and repeat floor areas per floor; `readDetails` unwraps `value`, prefers words over codes, and takes the shallowest match (max depth 3) so one floor's area never counts as the home's. A 400/404/405, or a lookup that times out, pauses certificate lookups for 10 minutes. Every EPC request has a time limit (search 15 s, certificate 10 s), so a hung API gives an `api_error` instead of a stuck popup. Certificate details are kept for 30 days in `chrome.storage.session` (`src/services/session-cache.ts`; session storage has its own quota and is emptied when Chrome closes), so a close home is never looked up twice. If some close homes got details and others did not (more than 10, or a failed lookup), the result can't be `exact`
- EPC potential: the matched home's certificate number is kept on the listing (`epcCertificateNumber`; a pick sets it, a new capture of a picked or exact home keeps it). At capture the background reads that certificate's energy side into `epcEnergy` (`src/services/epc-energy.ts`, pure, tested on the official sample certificates in `tests/fixtures/epc/`): `current_/potential_energy_efficiency_band`, `energy_rating_current/potential` (older names `current-energy-rating` etc. too) and `suggested_improvements` (name from `improvement_number` via `src/services/epc-improvements.ts`, generated from the government's ExternalDefinitions.xml, MIT; typical cost, yearly saving, rating after). One certificate answer fills both the details and the energy caches. Listings captured earlier get it from the listing page's Get EPC details button (`LOAD_EPC_ENERGY`; `findCertificateNumber` uses the close homes or searches the postcode for the same address). Shown on the listing page (bands in EPC chart colours, gap, "low rating with high potential" = E/F/G now and C or better potential, improvements), as "could be C" under the dashboard EPC, in the report and in CSV
- `addressConfidence`: `exact` when one home beats the rest by 2+ points with real evidence, else `best_guess`; `enrichmentDetail` says what it matched on
- On a `best_guess` the close homes are saved as `addressCandidates` (best guess first, max 15). The dashboard lets the user pick one (`src/services/address-choice.ts`), which sets `addressConfidence: 'user_choice'`; a new capture of the same listing with the same postcode keeps that pick unless it finds an `exact` match. When the saved listing already has an `exact` or `user_choice` address and the new capture has the same postcode, display address, bedrooms, type, floor area and number from the text, the background skips the EPC lookup and reuses it (`reuseKnownAddress`), so re-capturing to check the price is instant. A capture that gets no answer from the register (lookup off, no token, or an `api_error`) keeps the home found before with the same postcode (`keepKnownAddress` through `saveListing(…, { keepAddress: true })`), so checking the price never wipes a found address
- Listing floor area (`floorAreaSqm`) comes from Rightmove `sizings`, and on Zoopla from JSON-LD `floorSize`, else the page data's `floorArea` object or `sizeSqFeet`. Zoopla's `ingested.sizeSqft` is ignored: it is estimated from neighbouring homes
- When the site gives no size, `src/adapters/floor-area-text.ts` reads one from the description (all 3 sites) into `floorAreaFromText`. It is strict: the clause must say it is the whole home (or be the size alone), any room/garden/plot word rules it out, and sizes that disagree give null. The background uses it only when the "Find the size in the listing text" setting is on (default on); `floorAreaSource` records `listing` or `text`, and the match detail says "floor area from the description"
- Listing EPC band (`epcRating`) comes from Zoopla's `epcRating` field, Rightmove "EPC Rating: X" text in key features/description, and OpenRent's table row (`src/adapters/epc-band.ts`); a home with the same band gets +2. The listing's own rating is never replaced, and the certificate's rating is only borrowed on an exact match

## Storage (`src/services/storage.ts`)

- Uses `chrome.storage.local`
- Deduplicates by `source:listingId`
- Every read-change-write save (listings, settings, user data) runs under `withLock` (`src/services/storage-lock.ts`, `navigator.locks`, shared by all extension pages and the service worker), so two saves at once never drop one. Pipeline edits go through `updatePipeline`, which saves only the fields given; the listing page sends only the fields typed there and shows a stage changed elsewhere
- Price history: `saveListing` keeps every price seen for a listing in `priceHistory` (oldest first, a new point only when the price or qualifier changes, max 50; a listing saved before this existed starts from its old capture). `src/services/price-history.ts` (pure, tested) gives `priceChange` (first price to latest, % and direction; null until the price has moved), `latestMove` and `describeChange` ("Reduced £10,000 (−3.3%)"). Dates are the capture that first saw a price, not the day the agent changed it. Shown in the popup after a capture that finds a new price, on the dashboard (tag under the price, "Price reduced" count, price filter) and on the listing page (change line and history table)
- The site's own dates (Rightmove and Zoopla; OpenRent shows none): `listedOn` (YYYY-MM-DD first listed: Rightmove `analyticsInfo.analyticsProperty.added` "20260918", Zoopla `publishedOn`) and `portalPriceChanges` (date and `down`/`up`, no amounts: Zoopla `priceHistory.priceChanges` [`isPriceDrop`, `priceChangeDate`], Rightmove `listingHistory.listingUpdateReason` "Reduced on 12/10/2026" / "Reduced today|yesterday", latest only). Parsed in `src/adapters/listing-dates.ts` (pure, tested on strings from saved real pages). `withPriceHistory` adds the site changes up across captures (`cleanPortalChanges`, one per date and direction, max 50) and keeps `listedOn` when a capture lacks it. These feed feature 3 rather than a second tracker: `wasReduced` / `wasIncreased` / `priceMoved` (a captured change or a site change) drive the price filter and the "Price reduced" count, so a reduction shows on the first capture; the dashboard price tag falls back to the site's latest change ("Reduced 28 Aug 2026"); the listing page shows `describePortalChanges` under the price. New: `daysOnMarket` (from `listedOn`), shown under the captured date on the dashboard and in the listing header, a "days on the market" filter (`minDays`: 30/60/90/180+; homes with no site date are left out), a "Listed on Zoopla" timeline entry, an "On the market" report row, and CSV columns Listed On, Days On Market, Site Price Changes
- Settings: EPC API token, auto-enrich toggle, floor area from description toggle
- CSV export of all saved listings, with the match detail saved per listing, and First Price Seen / Price Change / Price History columns. Text cells starting with `= + - @` get a `'` so Excel won't run them; the popup adds a UTF-8 byte order mark

## Data flow

1. User opens a listing page → content script detects it, notifies background (badge turns green)
2. User clicks "Capture" in popup → popup sends `EXTRACT_LISTING` to content script
3. Content script runs the matching adapter → returns extracted data to popup
4. Popup sends `CAPTURE_AND_ENRICH` to background → background calls EPC API if enabled
5. Background saves enriched listing → returns to popup for display

## Tech stack

- WXT framework (Vite-based Chrome extension tooling)
- TypeScript
- Chrome Manifest V3
- No UI framework (vanilla DOM)
- Shared display helpers in `src/services/format.ts` (`formatMoney`, `SITE_NAMES`); storage keys are exported from `storage.ts` (`LISTINGS_KEY`, `SETTINGS_KEY`) and `user-data.ts` (`USER_DATA_KEY`, `listingKey`)
- Bump the version in `package.json` and `wxt.config.ts` with each PR, so `chrome://extensions` shows which build is loaded
